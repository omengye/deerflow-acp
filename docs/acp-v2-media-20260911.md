# ACP v2 图片与 Buzz 附件支持

交付日期：2026-09-11。

## 变更

- v2 Bridge 在初始化时将 Python daemon 的 prompt capabilities 转换为 v2 能力声明。存在视觉模型时声明 `capabilities.session.prompt.image`；当前会话仍须选择支持视觉的模型。
- daemon TCP、独立 Python stdio 和 Buzz v2 客户端允许读取最高 64 MiB 的 JSON 帧，覆盖每轮 40 MiB 图片的 Base64 编码及 v2 用户消息回显。
- Buzz v2 sidecar 保留 `imeta` 附件标签，使用官方 CLI 的 `media get` 完成鉴权下载；校验大小、SHA-256 和图片格式。
- 图片通过原生 ACP image block 传递。普通文件保存到工作区 `.buzz-attachments` 中，通过 `file://` ResourceLink 交给 DeerFlow 工具。
- 支持纯附件消息、文字与附件混合消息；原有频道提及、DM、发送者白名单规则继续生效。
- SQLite 自动增加附件标签列；重启保留待处理附件，重试复用已校验文件。无效附件通过原有持久化回复流程反馈，不运行模型。

## 限制与使用

Buzz 每条消息最多 8 个附件，合计不超过 40 MiB；每张图片最多 20 MiB，普通文件最多 25 MiB。DeerFlow 的资源链接大小配置可能进一步限制文件。

图片支持 JPG、PNG、WebP、GIF。模型配置需设 `supports_vision: true`，且模型服务真实支持视觉。文件通过工具读取，不承诺所有格式自动转换成文本。音频和视频暂不支持。

在 Buzz 输入框使用附件功能发送；消息正文里的普通 URL 不会自动当附件下载。需要支持 `buzz media get` 的官方 CLI。下载仅允许配置 relay 的媒体来源，CLI 不向重定向目标转发鉴权。

更新便携包后启动新 daemon，在 sidecar 的 `adapter.toml` 中将 `deerflow.command` 指向新包内 `deerflow-acp.exe`，保持 `protocol = "v2"`、`args = ["--protocol", "v2"]`，随后重启 sidecar。已有配置、身份环境变量和会话数据库应保留在原有私有位置，新发布包不包含这些数据。

缓存按 ACP 会话和 Buzz 事件组织，供后续回合继续访问；不再需要相关对话后可手动删除对应目录。共享工作区内的文件可被使用该工作区的其他会话访问。
