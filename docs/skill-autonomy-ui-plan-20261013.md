# 技能自动维护与设置页布局方案

日期：2026-10-13

状态：2026-10-14 已实施并完成本地 Release 构建、替换及重启。下列章节保留早期完整目标设计，实际交付范围见第 10 节。用户已确认本版 MVP 保留新技能首次发布及超范围变更的人工审核；P3 新技能自动发布不属于本版验收要求。当前分发检查见 `release-readiness-20261014.md`，本地部署不替代 GitHub 干净提交构建。

## 1. 产品决策

推荐产品方式为「自动维护」：系统自动学习、生成、审查和评测，符合已授权范围的改动自动采用；仅把必须由用户决定的事项交给用户。

对用户的承诺：

> 小改动自动验证和采用；需要扩大能力或授权范围时再询问。所有修改可追溯、可暂停、可撤销。

目标是减少用户决策次数，而不是减少校验步骤。模型给出的“低风险”“高置信度”不能独立构成发布授权。没有测试覆盖、没有独立证据或来源失效时，系统不得靠换名称、拆补丁、换来源、重复生成来绕过限制。

推荐界面使用三个方式：

| 方式 | 行为 | 面向人群 |
| --- | --- | --- |
| 自动维护（推荐） | 自动处理已授权且验证合格的改动，例外进入需要处理 | 日常用户 |
| 审核后采用 | 自动起草和验证，全部发布由用户确认 | 希望逐项控制的用户 |
| 关闭新维护 | 停止新的学习、生成和采用，已有技能继续可用 | 不希望后台维护的用户 |

“默认推荐”不等于升级后静默启用。已有用户保留原配置、预算和审核方式，切换时一次性确认可维护来源、费用上限和自动采用范围。按 2026-10-14 的追加要求，新桌面配置预设自动维护、固定范围及额度，并在设置页说明费用和审核边界，首次使用只需填写模型信息。迁移不得把现有 review 用户直接切成自动发布，也不得开启原本关闭的跨会话共享。

## 2. 当前实现及差距

以下为本次源码核对结果，不把规划能力表述为现有能力。

| 事项 | 已有实现 | 仍需建设 |
| --- | --- | --- |
| 技能资产 | SQLite 不可变版本、发布历史、导出视图、回滚 | 继续复用，不引入第二套文件权威来源 |
| 经验链路 | 提取、归并、匹配、发现、生成、审查及有界维护队列 | 防止上游提取耗尽下游预算；更清晰的证据阻塞解释 |
| 自动采用 | auto_patch 允许满足约束的已有受管技能小补丁 | 简单入口、就绪检查、覆盖率投影、多套件选择 |
| 新技能 | 自动生成候选，仍需人工发布 | 后续独立受限自动创建策略，不能复用 auto_patch 绕过限制 |
| 自动补丁观察 | 已有观察与回滚；质量判断主要依赖 operator_confirmed 证据 | 宿主可信自动评测证据，不能把普通运行成功算作质量提升 |
| 行为套件 | SDK 支持多个目标套件；原生 YAML 当前加载一个 suite_path | 可版本化的多目标套件注册表和覆盖展示 |
| 技能中心导航 | 已有 SettingsPage::DeerFlowSkillCenter；主侧栏底部有单独入口 | is_visible_in_navigation 当前未放行该设置页，需调整导航可见性 |
| 技能页 | 我的技能、待审核、生成记录、学习来源、发布历史 | 以能力与结果为主的四页结构、跨阶段记录、例外收件箱 |
| 其他生态技能 | 另有基于文件目录的 Skills 页，当前不在主设置导航中 | 作为“来源”的外部适配器保留，不与 SQLite 管理操作混用 |

现有打包的 code-documentation / newsletter-generation 示例套件指向 python-public 内置来源，不能直接当作任意 managed 技能已经具备评测覆盖。此前数据库快照中受管安装只占少数；首期必须如实展示覆盖范围，不能让“自动维护已开启”掩盖大部分目标仍无资格这一事实。

关键实现位置：

- `desktop-app/src/app.rs`：SettingsPage 及导航可见性。
- `desktop-app/src/app/settings.rs`：设置菜单、内容容器；普通设置当前最大宽度 760。
- `desktop-app/src/app/sidebar.rs`：底部技能中心快捷入口。
- `desktop-app/src/app/deerflow_settings/presentation.rs`：技能标签页、维护方式预设及页面路由。
- `desktop-app/src/app/deerflow_settings/skills.rs`：技能目录、管理与审核操作。
- `desktop-app/src/app/skills_page.rs`：外部文件技能目录，不能用其文件重命名逻辑操作受管技能。
- `go-harness/internal/skills/evolution/auto_patch_store.go`：自动采用条件。
- `go-harness/internal/skills/evolution/auto_patch_monitor.go`：采用后观察与回滚。
- `go-harness/internal/launch/behavior.go`：原生单套件加载。
- `go-harness/internal/learning`、`go-harness/internal/skillmaintenance`：经验、维护队列与预算。

## 3. 自动处理范围

### 3.1 首期默认策略

| 情况 | 系统动作 | 是否打扰用户 |
| --- | --- | --- |
| 已启用受管技能的 SKILL.md 正文小补丁 | 安全和质量审查、基线/候选对照、改善与零回归检查后自动采用 | 正常成功只记记录 |
| description 触发描述变更 | 额外执行正负触发用例；正文同时改变时还须正文改善 | 正常成功只记记录 |
| 单任务 review_draft | 自动审查、保存草案；等待独立证据，或提供自愿提前审核入口 | 不因草案生成就通知 |
| 没有适用可信套件 | 保留现版本，标记缺少覆盖；同类缺口聚合 | 持续阻塞时仅出现一个可处理事项 |
| 证据冲突或 unresolved | 等待后续真实任务提供可验证证据 | 不逐条要求用户确认经验 |
| 网络、限流、预算不足、目标正忙 | 按错误类型等待或有界重试 | 只有需要改凭证、配置等才通知 |
| 已确认泄密、越权、凭证写入或恶意指令 | 拒绝、隔离候选，保留脱敏原因 | 严重且可操作时提醒，不提供一键绕过 |
| 新技能、首次接管导入技能、内置覆盖、大改动、支持文件、删除或扩大权限 | 首期仍需人工确认或保持阻止；允许一条授权事项覆盖明确列出的来源/技能 | 进入“需要处理” |

自动采用仍须同时满足以下条件：

1. 来源和目标当前有效，用户授权范围覆盖该技能，候选与当前 head 完全一致。
2. 当前技能已启用、已受管；不是首次接管、内置覆盖或新能力创建。
3. 默认修改不超过 40 行，不修改支持文件、权限、来源和无关元数据。
4. 安全与质量审查通过，可信行为套件通过；有可证明的针对性改善且无回归。
5. 学习来源候选具备至少 2 个宿主认定的独立任务证据，窗口默认 30 天。
6. 候选不属于永久 review_draft 或人工裁决类别，未撤销、未过期且未被新版本替代。
7. 每日自动采用、维护预算、目标并发及观察期限制全部通过。

发布决定由宿主服务执行，在同一事务中校验、移动发布指针、记录决策并加入导出队列。模型和前端都不直接获得发布权限。

按修改类别路由，不给候选打一个总分后直接采用。删除权限说明、改变敏感数据处理方式或增加外部操作，即便只改一行，也不能因为满足 40 行限制而进入低风险通道。

### 3.2 减少草案对人工的依赖

现有 review_draft 的“必须人工审核”绑定必须保留，不能在后台改一个标志把旧草案变成可自动采用。

建议后续新增“证据成熟后继候选”路径：新的独立任务产生新的 pattern revision 后，重新审查来源并创建新候选；旧草案显示“已被后继候选替代”。原任务消费、计费和幂等键不退款、不重置，不得重复花同一证据。后继关系必须持久化，且受冷却、次数及预算限制。

这是待实现的状态转换，不是当前已有的自动重试能力。旧草案无需用户逐个驳回，未成熟草案也不长期霸占人工处理队列。

### 3.3 新技能尽量自动，但分阶段开放

首期不能宣称新技能自动发布。后续扩展独立的受限自动创建策略，并在一次性范围授权后允许满足全部条件的新技能自动采用：

- 仅在明确授权的 managed source 创建，仅有 SKILL.md；不含脚本、下载执行、凭证或新增工具权限。
- 初期仅覆盖事先声明的低风险类别，例如文本整理和固定格式转换；类别必须有宿主维护的可信测试模板。
- 至少 2 个独立任务来源；目录匹配确认没有可复用的已有技能；来源内名称、禁用记录、tombstone、在途候选及跨来源可见名称冲突均通过检查。
- 对照“无此技能”基线有改善，正负触发、相关技能误触发和行为回归用例均通过。
- 自动生成的测试只能作为候选测试建议，不能自动成为自己的可信评分标准。可信模板、断言和留出样本由宿主预先固定并版本化。
- 对受限类别实行运行时强制工具/作用域约束；纯文本不代表安全。若当前宿主不能隔离这些能力，则该类别只能保留待审，不能只写一句提示词声称已限制。
- 发布后先限工作区、小范围使用；扩大到全局需独立授权。新增运行时作用域与试运行选择器在实现前不得伪装成现有能力。
- 发生确定回归时停用新增技能并保留历史；已有技能则回滚到上一有效版本。

上网搜索、发送消息、提交代码、删除文件、安装依赖、修改基础设施等有外部效果的能力，不纳入首批自动创建白名单。技能自动采用永远不替代实际工具执行的权限检查。

## 4. 学习、队列与成本

保留本机已设置的上限，不因切换维护方式偷偷增加预算：维护每日 1000 次调用 / 600 万 Token；学习每日 50 次 / 100 万 Token；单任务 600 秒；维护并发上限 5。2026-10-14 用户进一步要求新桌面配置沿用这些额度，首次初始化模板据此同步；已有用户的额度仍不自动改写。

保留发现规则：2 个独立任务、30 天窗口、1 小时目标冷却、每天最多 10 个提案、待处理上限 5。自动采用初期每天最多 2 次，默认观察 72 小时、至少 3 个合格观察、连续 2 个确定质量失败触发回滚。观察期内同目标不得叠加未经稳定性确认的自动修改。

新增预算公平调度：

- 学习 50 次调用可使用提取 20、归并 15、匹配 15 的软份额；只是容量预留，不是必须花完的目标，也不再叠加额外总预算。
- 允许借用空闲阶段份额，但要检查下游队列并保护已有候选的验证工作。Token 预算也必须预留，不能只分调用次数。
- 调度优先级先恢复可复用的评测/发布工作，再匹配、归并，最后进行新的批量提取；设置最大等待以防提取永久饥饿。
- 正常交互优先于维护。5 是并发上限，根据宿主负载和提供商限制降速，不代表持续发出 5 个请求。
- 区分稍后继续的预算等待与终态失败。新等待机制不得重置原 job 的 deadline、已计费调用或尝试次数；需要后继 job 时，必须显式记录关系并重新核验来源，不复活旧终态 job。
- 按目标与原因合并重复草案/异常通知；新的候选版本保留完整记录。未经新设计验证前，不放松现有共享 pending cap，也不另建无限量“后台待审”池绕过它。
- source_bounds 不采用直接放宽输入的方法。优先识别具体超限维度，保留原引用并做有界任务视图；无法验证的部分不进入发布证据。

## 5. 可信评测与发布后观察

避免让用户为每个技能手工写一个 JSON 套件。建设宿主管理的测试模板与多目标套件注册表：

1. 按任务类别安装可信模板，由宿主程序生成固定断言并绑定来源、技能、基线和套件版本。
2. 候选作者只提交技能改动；审查模型使用独立上下文；测试期望和留出答案不进入候选模型上下文。
3. 冻结用例后比较 baseline 与 candidate。描述变化必须检查正例、负例和竞争技能，不能只验证“会选中自己”。
4. 不具备可信覆盖时自动维护处于“部分可用”，显示阻塞原因，绝不当作评测通过。
5. 所有评测使用临时工作区和 fixture 工具，不对真实第三方服务执行有副作用的回放。

现有发布后监控只把特定的 operator_confirmed 证据算作质量判断。后续增加独立的 host_evaluated 证据类型，固定测试断言、输入哈希、版本与结果，可驱动自动回滚，但不得伪造成人工反馈。普通“任务完成”、没有投诉、模型自评高分都不是质量成功票。

观察期结束仍无充分证据时显示“观察结束，质量证据不足”，不能显示“已证明更好”。保持可回滚的当前版本；严重安全或完整性问题使用独立撤销机制。用户暂停自动维护时停止新的付费工作和发布，保留无付费的安全观察与手动回滚；若连该监控也要停，需另外明确说明。

## 6. 界面信息架构

### 6.1 导航归位

设置左侧顺序建议为：常规、模型、工具、技能、外观、高级。

- 放行 SettingsPage::DeerFlowSkillCenter 的导航可见性，显示名称统一为“技能”。
- 移除聊天主侧栏底部常驻的“技能中心”文字按钮，保留设置入口、命令面板搜索和聊天内技能详情跳转。
- 设置入口仅在存在可操作事项时显示角标；不把正常学习、冷却或草案计入红点。
- 旧技能中心入口和搜索词继续重定向到新页，避免旧链接失效。
- 外部生态文件技能放在“自动化设置 > 技能来源 > 外部技能库”，明确区分导入来源与 DeerFlow 当前生效版本。

### 6.2 页面框架

```text
设置
  常规          技能                          [自动维护 · 部分可用] [暂停维护]
  模型          自动处理已授权的小改动；需要扩大范围时再询问。
  工具
> 技能          我的技能 | 进化记录 | 需要处理（数量） | 自动化设置
  外观          ---------------------------------------------------------
  高级          搜索技能                         来源筛选 / 状态筛选
                ---------------------------------------------------------
                技能列表                 | 选中技能详情
                名称、简述               | 适用场景、当前状态
                来源、启用状态           | 当前版本、作用域、维护资格
                最近变更                 | 最近改了什么、为什么采用
                                         | [查看差异] [版本历史] [停用]
```

图中状态和数量仅为布局占位，不代表本机已经开启自动维护或已经产生自动采用记录。

技能中心使用专属宽内容容器，建议最大宽度 1120，而不是复用普通表单的 760 宽度。设置菜单约 176，技能列表约 280～320，详情占剩余空间；空间不足时先取消并排详情，进入带返回按钮的单列详情。手机/窄屏使用设置选择器、可换行的标签及列表到详情导航，不缩小文字硬塞三栏。

复用现有 Theme、字号缩放和原生控件：中性色表面、珊瑚色只作少量强调，绿/黄/红必须伴随状态文字；不引入营销大卡片、新字体体系或独立配色。主要内容是技能和变更，不是虚假的“自进化分数”。

### 6.3 四个页面

| 页面 | 默认展示 | 详情与操作 |
| --- | --- | --- |
| 我的技能 | 当前启用、作用域、来源、最近变更；区分受管和导入技能 | 内容、有效版本、自动维护资格、差异、历史、停用与回滚 |
| 进化记录 | 按一次改进串起发现、生成、评测、采用、观察；默认优先采用和回滚 | 来源摘要、证据、测试差异、模型费用、完整审计；学习中间记录折叠 |
| 需要处理 | 仅真正需要决策的事项，优先高风险与授权阻塞 | 一句话说明为什么需要你、推荐动作、确认范围、影响及差异；允许忽略和暂停该技能维护 |
| 自动化设置 | 维护方式、实际生效状态、来源范围、费用上限、就绪检查 | 高级区域放重复阈值、冷却、队列、模型路由、套件和来源编辑 |

“我的技能”默认打开。进化记录不再让用户分别跳转生成记录、学习来源和发布历史才能理解一次改进。原始数据入口保留在记录详情中。

技能详情的回滚操作先重新读取当前 head，展示目标版本及影响，然后一次确认提交 CAS 请求。回滚后禁止原候选自动再次采用；后续新的合法候选必须重新验证。新技能的撤销显示“停用此技能”，不伪装成存在上一个内容版本。

### 6.4 自动化设置的默认层级

首屏仅展示：

1. 维护方式及准确范围说明。
2. 实际状态：已就绪 / 部分可用 / 已暂停 / 等待应用；附最重要的一个原因。
3. 自动采用的来源与技能范围，默认不扩大到外部来源或内置覆盖。
4. 维护总额度和学习子额度，标明“包含于总额度”，展示今日使用量与下次重置时间。
5. “保存并应用”及配置变更摘要；切换预设不覆写用户预算或额外授权。

后台已应用的配置 revision 与编辑草稿分别展示。不能仅凭 YAML 保存成功就显示“自动维护已开启”。缺套件、目标非 managed、运行服务尚未加载新配置等应分别可见。基础参数采用保守预设，不把数十个布尔开关直接摊给用户。

### 6.5 通知规则

| 事件 | 展示方式 |
| --- | --- |
| 合格小补丁自动采用 | 进化记录；不弹窗、不抢焦点、不出现待处理角标 |
| 例行提取、等待冷却、短暂限流 | 仅详细记录 |
| 新的人工决定事项 | 设置角标；按目标和原因去重，每个新事项最多一次非模态提醒 |
| 自动回滚或安全阻止 | 一次非模态提醒，说明当前可用版本和是否需要用户动作 |
| 凭证错误、长期服务故障 | 聚合服务级通知，不给每个技能重复报错 |
| 今日预算耗尽 | 页面显示下次恢复时间；仅需要改设置时提示，不按每个 job 弹窗 |

默认不推送每日总结；用户可选择摘要或完全静音。角标使用宿主聚合的当前授权来源总数，不使用当前分页的行数冒充总数。已读状态按用户资料和事件持久化，多窗口避免重复提醒。

等待额度、冷却或补充证据的工作显示在进化记录，不显示为红色失败。“需要处理”只接收用户有能力解决且确有必要决策的事项。服务不可达或统计尚未加载时显示“暂不可用”，不能把未知计数显示为零。

## 7. 服务、存储和性能设计

所有新增名称都是拟议接口或表，不代表当前 API 已存在。

- 复用现有 proposal/publication/head/maintenance 表作为事实来源。新的 `df_skill_policy_decisions` 只保存带策略版本的决定、原因代码、证据摘要和目标 head，不复制技能正文或完整聊天。
- 增加维护就绪状态投影，返回请求的方式、实际生效方式、配置 revision、可自动采用目标及阻塞原因。
- 增加跨阶段活动查询与需要处理计数投影，均按当前授权来源过滤，支持分页、增量游标和版本失效。
- 需要处理列表是状态投影；若物化，须与决定、失效及撤销在事务或 outbox 中保持一致，不能形成第二套审批状态。
- 所有变更接口校验来源身份、目标 head、policy revision、请求幂等键。事务重试不得重复发布；无确认结果的请求先查询原 receipt，而不是盲目重发。
- SQLite 继续是受管技能唯一权威来源，导出失败不回滚已发布技能，也不将旧导出文件重新导入。
- GPUI 渲染只读缓存，不做 SQLite 查询、文件遍历、模型调用或同步 IPC。后台合并加载目录与计数，使用 generation counter 丢弃过期响应。
- 列表虚拟化；增量事件刷新已打开页面，不对每个技能单独高频轮询。后台窗口和关闭页面降低刷新频率。
- 键盘可完成导航、筛选、详情、确认和返回；状态不只靠颜色；支持字号缩放、减少动态效果和窄窗口。

## 8. 分期交付

### P0：入口、可见性和诊断

- 技能中心进入设置菜单，移除常驻主侧栏按钮；迁移为四页结构并保留旧路由。
- 增加真实就绪状态、阻塞原因及跨阶段进化记录。先用已有数据，不伪装自动采用能力。
- 明确外部文件技能与受管技能边界；保留用户现有预算、作用域及 review 配置。

验收：旧入口可达；分页计数不误导；无任务时有解释性空态；渲染无同步 I/O；键盘和窄窗口可用。

### P1：已有技能自动维护闭环

- 增加自动维护预设、一次性范围授权和有效配置回执。
- 多目标可信套件注册、来源/目标就绪判断、后台审查、既有 auto_patch 路径与回滚。
- 预算公平调度、合并异常提醒、操作幂等、暂停新付费工作并保留安全监控。

验收：代表性已有技能从新证据到自动采用无需逐项点击；缺套件不发布；超范围不发布；重复事件/重启不重复采用；配置变更及来源撤销能阻止在途旧候选生效。

### P2：证据成熟和自动质量观察

- 草案成熟后的新 revision/后继候选路径，保持原审计和消费语义。
- 新增宿主可信评测结果来源，自动评测回归可触发回滚；网络/配额错误不能算质量失败。
- 对 source_bounds、unresolved 做保守来源修复与可解释诊断，不直接放松安全规则。

验收：旧 review_draft 不被重新标记后直接发布；成熟后继候选依赖新证据；回滚不会覆盖用户后续手动版本；无观察样本不得记为成功。

### P3：低风险新技能受限自动采用

- 独立发布策略、受限类别、运行时权限与作用域隔离、无技能基线和竞争技能测试。
- 获得范围授权后，低风险新技能可自动采用；高风险和未覆盖类别继续人工。

验收：命名冲突、tombstone、重复创建和跨来源绕过被拒绝；外部副作用无法通过新技能获得权限；停用和重新启用可追溯；真实留出任务达标后才扩大开放。

## 9. 成功标准与禁止事项

统计资格覆盖率、具备资格的候选自动采用率、每次成功改进需要的人工作业数、生成到采用时延、误触发率、实际回归率、回滚恢复时延及每次有效改进成本。分别报告后台失败与安全拒绝，不把全部失败归为技能质量问题。

自动化率的分母必须公开，不能通过隐藏未覆盖技能或积压候选来制造高自动化数字。上线前冻结代表性任务和留出集；真实模型质量评测的预算与上线门槛单独确认，不把确定性接线测试当语义质量验收。

必须通过的反例：包含密钥的候选、指令注入、先生成答案再改测试、来源撤销、并发 head 改变、重复任务伪造独立证据、预算跨日、重启恢复、回滚时目标已变、外部文件适配器错误写入受管源、正常运行成功被误当质量提升。

实施优先级为 P0 + P1，再处理 P2；P3 必须等可信覆盖与运行时隔离验证完成。不能只改默认 mode 为 auto_patch 就声称“全自动技能进化”。

## 10. 本轮实际交付（2026-10-14）

### 已实现

- 设置菜单中显示“技能”，移除主侧栏常驻技能中心按钮；保留原设置页路由和跳转。
- 四个页签为“我的技能 / 进化记录 / 需要处理 / 自动化设置”。技能页最大宽度 1120；目录与详情采用可换行布局，窄空间顺序堆叠，可收起详情。使用原生主题和支持键盘激活的已有按钮，不做界面 I/O。
- 进入页面或切换页签后串行加载只读状态和对应列表；沿用服务身份与 generation 检查丢弃过期响应。没有持续轮询、弹窗或聊天通知。
- 推荐“自动维护”预设只修改编辑草稿，沿用现有“保存并应用”授权回执；不静默迁移 review，不增加预算、不扩展来源或跨会话授权。
- 就绪状态由宿主根据当前目录、受管状态、来源许可、内置边界及可信套件投影。没有覆盖则“部分可用”；新技能始终显示需要审核。
- `skill.auto_patch.status.readiness` 增加全部授权来源的 `pending_review / needs_attention / waiting_candidates`。需要处理数量不再是当前页行数。
- `proposal.list` 支持可选 `needs_attention` 布尔过滤（只允许搭配 pending_review）；分页游标绑定筛选和当前策略。候选列表返回只读 disposition，旧服务无此能力时显示未知并回退旧查询。
- 证据草案、观察等待、日发布额度等待及后台检查不算人工待办。发布器记录按候选状态版本与策略身份绑定的阻塞原因；这些投影不会授权发布，也不会替代事务中的重新校验。
- 原有自动补丁对普通来源与学习来源统一要求真实针对性改善、零回归和严格元数据边界；内置来源不能自动采用。description 变化仍须可信正负触发对照。不是单纯把两个通过的变体当成改善。
- 原生 suite_path 兼容单套件和 `skill-behavior-registry-v1` 内嵌注册表（1–32 目标，总文件不超过 1 MiB）。重复 JSON 键、重复目标、未知字段和未授权来源均拒绝；没有把生成模型提交的测试变成可信测试。
- 已采用补丁的无付费观察在关闭新自动发布后继续运行；保留原 CAS 回滚和 operator_confirmed 质量归因。服务整体停止时自然无法运行监控。
- 共享队列优先行为评测、生成、匹配、归并、提取；每五次成功 claim 给一次 FIFO 服务。学习调度对下游保留 30% 归并、30% 匹配软份额（全部下游忙时提取约 40%），调用与已收费 Token 同时参与；空闲份额可借用。匹配不被上游预留阻塞。硬额度和逐调用预留不变；软份额不是额外额度或精确花费保证。
- 已排队的学习任务可在 claim 前等待额度，不消耗新 attempt 或重设 deadline；已有结果进入原校验和 ACK 路径。并发中的大调用可能越过软份额，但不能越过硬额度；逐调用硬额度拒绝仍沿用原终态语义。
- 已有技能 review_draft 可被证据成熟后继候选替代，必须同 pattern 的新 revision、足够的未消费独立 episode、当前 head 一致及旧生成已完成。仍受冷却、日次数与共享 pending cap 约束。替代旧草案、入队与持久化前后继关系在同事务内完成；失败全部回滚，不退证据、不退费用。新技能和人工裁决候选不走此路径。
